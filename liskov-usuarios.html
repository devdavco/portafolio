SOLID — Principio L

LSP en un sistema de usuarios

Ejemplo sencillo: un usuario invitado no puede cambiar su contraseña, y eso rompe el contrato de la clase base.

Tenemos una app con dos tipos de usuario: registrados e invitados. Ambos pueden hacer login(), pero solo los registrados tienen cuenta y pueden cambiarPassword() o cerrarSesion(). El problema ocurre cuando ambos heredan de la misma clase base que promete esas acciones.

❌ Violación — UsuarioInvitado

UsuarioInvitado extiende Usuario pero lanza una excepción en cambiarPassword() porque los invitados no tienen cuenta. El sistema que gestiona usuarios no lo sabe y explota en runtime.

Usuario.java 
public class Usuario {
    protected String nombre;
    protected String email;

    public Usuario(String nombre, String email) {
        this.nombre = nombre;
        this.email  = email;
    }

    public void login() {
        System.out.println(nombre + " ha iniciado sesión");
    }

    public void cambiarPassword(String nueva) {
        System.out.println("Contraseña actualizada");
    }

    public void cerrarSesion() {
        System.out.println(nombre + " ha cerrado sesión");
    }
}
UsuarioInvitado.java Viola LSP 
public class UsuarioInvitado extends Usuario {

    public UsuarioInvitado() {
        super("Invitado", "");
    }

    @Override
    public void cambiarPassword(String nueva) {
        // ❌ los invitados no tienen cuenta — rompe el contrato
        throw new UnsupportedOperationException(
            "Los usuarios invitados no pueden cambiar su contraseña"
        );
    }

    @Override
    public void cerrarSesion() {
        throw new UnsupportedOperationException(
            "Los usuarios invitados no tienen sesión activa"
        );
    }
}
GestorCuenta.java Explota en runtime 
public class GestorCuenta {

    // espera cualquier Usuario y asume que puede gestionar su cuenta
    public static void actualizarCuenta(Usuario u, String nuevaPassword) {
        u.cambiarPassword(nuevaPassword); // 💥 si u es UsuarioInvitado
        u.cerrarSesion();                  // 💥 también falla
    }

    public static void main(String[] args) {
        Usuario david    = new UsuarioRegistrado("David", "david@mail.com", "1234");
        Usuario invitado = new UsuarioInvitado();

        actualizarCuenta(david,    "nueva123"); // ✅ funciona
        actualizarCuenta(invitado, "nueva123"); // ❌ UnsupportedOperationException
    }
}

El problema

GestorCuenta confía en que todo Usuario puede gestionar su cuenta. UsuarioInvitado hereda esa promesa pero no puede cumplirla — el error aparece solo en runtime.

✅ Solución — Interfaz CuentaEditable

Usuario solo define lo que todos comparten: login(). Los métodos de gestión de cuenta se mueven a la interfaz CuentaEditable, que solo implementa UsuarioRegistrado. GestorCuenta ahora exige CuentaEditable — el compilador bloquea que un invitado entre donde no debe.

Usuario.java 
public class Usuario {
    protected String nombre;
    protected String email;

    public Usuario(String nombre, String email) {
        this.nombre = nombre;
        this.email  = email;
    }

    // solo lo que todos los usuarios comparten
    public void login() {
        System.out.println(nombre + " ha iniciado sesión");
    }
}
CuentaEditable.java 
public interface CuentaEditable {
    void cambiarPassword(String nueva);
    void cerrarSesion();
}
UsuarioRegistrado.java 
public class UsuarioRegistrado extends Usuario implements CuentaEditable {
    private String password;

    public UsuarioRegistrado(String nombre, String email, String password) {
        super(nombre, email);
        this.password = password;
    }

    @Override
    public void cambiarPassword(String nueva) {
        this.password = nueva;
        System.out.println("Contraseña actualizada para " + nombre);
    }

    @Override
    public void cerrarSesion() {
        System.out.println(nombre + " ha cerrado sesión");
    }
}
UsuarioInvitado.java 
public class UsuarioInvitado extends Usuario {
    // no implementa CuentaEditable — no promete lo que no puede cumplir ✅
    public UsuarioInvitado() {
        super("Invitado", "");
    }
}
GestorCuenta.java Correcto 
public class GestorCuenta {

    // ahora exige CuentaEditable — invitados no pueden entrar aquí
    public static void actualizarCuenta(CuentaEditable u, String nuevaPassword) {
        u.cambiarPassword(nuevaPassword);
        u.cerrarSesion();
    }

    public static void main(String[] args) {
        UsuarioRegistrado david    = new UsuarioRegistrado("David", "david@mail.com", "1234");
        UsuarioInvitado   invitado = new UsuarioInvitado();

        invitado.login();  // ✅ los invitados sí pueden hacer login
        david.login();     // ✅

        actualizarCuenta(david,    "nueva123"); // ✅ funciona
        actualizarCuenta(invitado, "nueva123"); // ❌ error de compilación
    }
}

La solución

El compilador bloquea que un UsuarioInvitado entre a GestorCuenta. Ambos tipos siguen siendo Usuario y pueden hacer login(), pero solo el registrado promete gestionar su cuenta.
